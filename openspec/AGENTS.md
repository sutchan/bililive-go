# OpenSpec 说明

本说明适用于使用 OpenSpec 进行规范驱动开发的 AI 编码助手。
## TL;DR 快速检查清单
- 搜索现有工作：`openspec spec list --long`、`openspec list`（仅对全文搜索使用 `rg`）
- 确定范围：新功能 vs 修改现有功能
- 选择唯一 `change-id`：kebab-case 格式，动词开头（`add-`、`update-`、`remove-`、`refactor-`）
- 搭建脚手架：`proposal.md`、`tasks.md`、`design.md`（仅在需要时），以及每个受影响功能的增量规范
- 编写增量：使用 `## ADDED|MODIFIED|REMOVED|RENAMED Requirements`；每个需求至少包含一个 `#### Scenario:`
- 验证：`openspec validate [change-id] --strict` 并修复问题
- 请求批准：在提案批准前不要开始实施
## 三阶段工作流

### 阶段 1：创建变更
当您需要以下操作时创建提案：
- 添加功能或功能
- 进行破坏性变更（API、架构）
- 更改架构或模块
- 优化性能（改变行为）
- 更新安全模式

触发条件（示例）：
- "帮我创建一个变更提案"
- "帮我规划一个变更"
- "帮我创建一个提案"
- "我想创建一个规范提案"
- "我想创建一个规范"

宽松匹配指导：
- 包含以下任意一项：`proposal`、`change`、`spec`
- 包含以下任意一项：`create`、`plan`、`make`、`start`、`help`

跳过提案的情况：
- 错误修复（恢复预期行为）
- 拼写错误、格式、注释
- 依赖更新（非破坏性）
- 配置变更
- 现有行为的测试
**工作流**
1. 查看 `openspec/project.md`、`openspec list` 以及 `openspec list --specs` 以了解当前上下文。
2. 选择唯一的动词开头 `change-id`，并在 `openspec/changes/<id>/` 下搭建 `proposal.md`、`tasks.md`、可选的 `design.md` 和规范增量。
3. 使用 `## ADDED|MODIFIED|REMOVED Requirements` 起草规范增量，每个需求至少包含一个 `#### Scenario:`。
4. 运行 `openspec validate <id> --strict` 并在分享提案前解决所有问题。
### 阶段 2：实施变更
将这些步骤作为 TODO 跟踪并逐一完成：
1. **阅读 proposal.md** - 了解正在构建的内容
2. **阅读 design.md**（如果存在）- 查看技术决策
3. **阅读 tasks.md** - 获取实施检查清单
4. **按顺序实施任务** - 按顺序完成
5. **确认完成** - 确保在更新状态之前完成 `tasks.md` 中的每个项目
6. **更新检查清单** - 所有工作完成后，将每个任务设置为 `[x]`，以便列表反映实际情况
7. **批准门控** - 在提案经过审查和批准之前，不要开始实施
### 阶段 3：归档变更
部署后，创建单独的 PR 以：
- 移动 `changes/[name]/` 到 `changes/archive/YYYY-MM-DD-[name]/`
- 如果功能变更，更新 `specs/`
- 对于仅工具变更，使用 `openspec archive <change-id> --skip-specs --yes`（始终明确传递变更 ID）
- 运行 `openspec validate --strict` 以确认归档变更通过检查
## 任何任务之前

**上下文检查清单：**
- [ ] 阅读 `specs/[capability]/spec.md` 中的相关规范
- [ ] 检查 `changes/` 中是否存在待处理的变更冲突
- [ ] 阅读 `openspec/project.md` 了解约定
- [ ] 运行 `openspec list` 查看活动变更
- [ ] 运行 `openspec list --specs` 查看现有规范
- [ ] 运行 `openspec validate --strict` 检查整体一致性

## 规范格式

### 变更提案格式

每个变更提案必须包含：

1. **标题**：简洁描述变更
2. **变更 ID**：唯一标识符（kebab-case，动词开头）
3. **背景**：为什么需要此变更
4. **目标**：变更的预期结果
5. **范围**：受影响的功能/模块
6. **风险评估**：潜在风险和缓解措施
7. **验收标准**：如何确认变更成功
8. **依赖关系**：与其他变更或外部依赖的关系

### 增量规范格式

每个受影响的功能必须有一个增量规范文件，使用以下格式：

```markdown
# [功能名称] 增量规范

## MODIFIED Requirements

### [需求 ID]：[需求描述]

#### Scenario: [场景描述]

Given [前提条件]
When [触发事件]
Then [预期结果]

## ADDED Requirements

### [需求 ID]：[需求描述]

#### Scenario: [场景描述]

Given [前提条件]
When [触发事件]
Then [预期结果]
```

## 验证规则

- 所有文件必须使用 UTF-8 编码
- 所有 Markdown 文件必须通过 `markdownlint` 检查
- 所有变更 ID 必须唯一
- 所有需求必须包含至少一个场景
- 所有场景必须遵循 Given-When-Then 格式
- 所有链接必须有效
- 所有代码示例必须语法正确

## 最佳实践

- 保持规范简洁明了
- 专注于 "什么" 而不是 "如何"
- 使用具体的场景和示例
- 避免模糊的语言
- 定期更新规范以反映实际实现
- 与团队成员协作编写和审查规范

## 常见问题

### 如何处理冲突的变更？

如果您的变更与另一个待处理的变更冲突：
1. 与相关变更的作者讨论
2. 确定优先级
3. 调整您的变更范围或实现方式
4. 在提案中记录冲突和解决方案

### 何时需要创建 design.md？

当变更涉及：
- 复杂的架构决策
- 多种实现方案的选择
- 与现有系统的复杂集成
- 性能或安全关键的设计

### 如何处理破坏性变更？

破坏性变更需要：
1. 在提案中明确标记为 "破坏性变更"
2. 提供详细的迁移指南
3. 考虑提供向后兼容层
4. 获得更高层级的批准

## 术语表

- **变更 ID**：变更的唯一标识符，用于跟踪和管理变更
- **增量规范**：对现有规范的修改或添加，用于描述变更
- **场景**：使用 Given-When-Then 格式描述的具体用例
- **验收标准**：确认变更成功的可测量标准
- **破坏性变更**：导致现有功能或 API 无法正常工作的变更

## 工具命令

- `openspec spec list [--long]`：列出所有规范
- `openspec list [--specs]`：列出所有活动变更
- `openspec validate [change-id] [--strict]`：验证变更规范
- `openspec create [change-id]`：创建变更脚手架
- `openspec archive [change-id] [--skip-specs] [--yes]`：归档变更
- `openspec update`：更新说明文档

## 版本控制

- 所有规范文件必须使用 Git 进行版本控制
- 规范变更应与代码变更在同一 PR 中提交
- 规范文件的版本应与代码版本保持一致
- 归档的变更应保留在代码库中，以便历史参考
